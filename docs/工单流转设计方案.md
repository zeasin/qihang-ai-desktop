## 1. 背景与现状

| 能力 | 现状 | 位置 |
|---|---|---|
| 状态模型 | 保留状态链 `待处理 → 处理中 → [自定义流转态] → 已完成 → [自定义终态] → 已关闭` | `useTickets.ts` / `ticket-tracker.ts` / `ticket-link.ts` |
| 状态变更留痕 | `ticket_logs` 流水（action/status/update…），挂在 `db.ds.onRecordSave` | `ticket-tracker.ts` |
| 待办联动 | 终态收尾 / 退回复活 | `ticket-tracker.ts` |
| 承诺时间 → 提醒 | 24h 当场建 + 每日扫描兜底 | `ticket-link.ts` |
| webhook 发送 | `sendViaWebhook(url, message)` 飞书文本消息，url 可任意 | `feishu.ts:18` |
| 处理人 | 自由文本字段，无行为 | — |
| **缺失** | 节点实例（谁在处理、处理了多久、结果如何）、处理人配置、流转通知 | — |

**v1 草案被否的点**：只加一张「流转规则表」（每状态一行 owner/notify），处理过程仍然只有
ticket_logs 里零散的流水——没有「节点」概念，查「这单现在到谁手里、卡了多久、上一棒结论
是什么」要自己拼日志。用户要的是完整的一手一棒记录。

## 2. 数据模型：三张表

### 2.1 处理人节点表 `ticket_handlers`（人 = 节点 = 名字+webhook 一体）

**核心心智模型：处理人（节点）是配置的基本单位。** 一个处理人节点 =
「这个名字的人/岗」+「通知发到他的 webhook」——两者捆绑，不可拆分配置。

```
ticket_handlers（处理人节点）
┌──────────────┬────────────────────────────────────────────┐
│ id           │ 主键                                        │
│ name         │ 节点名/处理人名（与工单「处理人」字段对齐，唯一）│
│ webhook_url  │ 通知目标 webhook（流转到该节点时触发）         │
│ enabled      │ 启用（0/1）                                 │
│ remark       │ 备注（如「售前组」「技术支持-张三」）           │
│ created_at / updated_at                                   │
└──────────────┴────────────────────────────────────────────┘
```

- **流转到某个处理人节点 → 自动通知到该节点的 webhook_url**。选中节点这个动作
  同时决定了负责人和通知出口，不存在「选了人但忘了配通知」的中间态。
- 节点可以是「人」也可以是「岗」（如「售前组」一个 webhook 群机器人）——名字只是标识。
- webhook 没配或为空：只流转不通知（不报错，留痕）。
- webhook 换地址改这一行即可；节点名在历史里靠 handler_name 冗余保持不变。

### 2.2 流转方向：不做「状态规则」，处理人手动选（2026-11-21 用户拍板）

v1/v2 都想过一张「状态 → 默认处理人」的规则表（ticket_flow_rules）——
**作废**。讨论结论：想不到「哪个状态固定归谁」的真实场景，单人使用时人就是我自己，
多岗协作时人也是看事情指派，不是看状态指派。规则表会变成一张永远只配一两行的摆设。

**改为「手动选」**：状态变更时的处理人永远是「上一棒人」或「这次保存里填的处理人」，
**通知的触发点直接挂在「处理人变了」这件事上**：

```
处理人字段从空/旧值 → 新值（人工填/改）
  → 新值能匹配到处理人节点表里的 name
  → 该节点配了 webhook_url
  → 发通知到该 webhook
```

不再有「状态规则命中才通知」——**谁被指派了谁就收到通知**，直觉、零配置。
状态变更本身不触发通知（除非处理人同步变了）。

**为什么这样更好**：
1. 砍掉 ticket_flow_rules 整表，数据模型从三表变两表；
2. 通知语义贴近真实诉求：「这单交给你了」才是该被通知的事，「状态变到处理中」不是；
3. AI/飞书建单时填了处理人（如「给张三」），同样自动命中通知——钩子在数据层，来源无关；
4. 规则需求万一将来冒出来（「处理中固定默认我自己」），加一张同名表就回来了，
   节点实例表不破坏。

### 2.3 流转节点实例表 `ticket_flow_nodes`（核心，一次流转一行）

这是用户要的「完整记录」：**每个节点 = 工单在某状态停留的一段生命周期**。

```
ticket_flow_nodes
┌──────────────────┬────────────────────────────────────────────┐
│ id               │ 主键                                        │
│ dataset_id       │ 工单数据集 id（TEXT，与 ticket_logs 同口径）  │
│ record_id        │ 工单记录 id                                 │
│ node_index       │ 节点序号（从 1 递增，按工单内排序）             │
│ status           │ 本节点的状态（= 流转到时的目标状态）            │
│ handler_name     │ 本节点处理人（冗余名字，防止处理人改名对不上历史）│
│ handler_id       │ 处理人 id（可空：手动填的名字没建处理人档案）    │
│ entered_at       │ 进入本节点时间（= 状态变更时刻）               │
│ exited_at        │ 离开本节点时间（= 下一次状态变更时刻）。当前节点为 NULL │
│ duration_minutes │ 停留分钟数（离开时算出写入，当前节点实时算）     │
│ result           │ 处理结果（离开本节点时填写，自由文本）           │
│ result_kind      │ 结果分类：ok / back（打回）/ skip（跳过）/ auto │
│ trigger          │ 触发方式：ui / ai / feishu / auto（规则自动改人）│
│ notified         │ 通知是否发送成功：0 未发 / 1 成功 / -1 失败     │
│ notify_error     │ 通知失败原因（留排查）                        │
│ created_at       │                                            │
└──────────────────┴────────────────────────────────────────────┘
```

**节点生命周期**（一次状态变更 A → B 的完整动作）：

1. **关闭上一节点**：找到该工单 `exited_at IS NULL` 的最新节点（状态应为 A），
   写 `exited_at = now`、`duration_minutes = now - entered_at`、
   `result = <本次处理结果>`、`result_kind`。
2. **开启新节点**：插入 B 状态行，`node_index = 上一行+1`，
   handler 取落库后的「处理人」字段（人工填的/AI 填的，不再有规则覆盖），
   `entered_at = now`，`notified` 按通知结果回写。
3. **通知**：处理人**变了**且新处理人能匹配节点表 + 有 webhook
   → `sendViaWebhook(handler.webhook_url, 文案)`。
   （通知挂在「处理人变更」上，不是「状态变更」上——见 §2.2。）

**「处理结果」从哪来**：状态变更的入口是人写的——快捷推进/编辑弹窗改状态时，
弹一个可选的「处理结果」输入（快捷推进第一次点不填=空结果，编辑弹窗里有专门输入框）。
也接受从工单「备注」字段尾部截取（用户不想弹框时，备注即结果）。AI/飞书改状态时，
把触发说明写进 result（如「飞书指令：已完成」）。

### 2.4 两张表与 ticket_logs 的关系

- `ticket_logs` 保持现状（细节流水：字段级变更、备注、关联待办……），不重复记录流转语义。
- `ticket_flow_nodes` 是**结构化**的节点账：一单到过哪些状态、每站谁负责、停多久、结果是什么——
  一条 SQL 就能回答「这单卡在哪」「平均处理时长」「谁手里压了最多单」。
- 工单弹窗的「处理记录」区读 ticket_logs；新增的「流转历史」时间轴读 ticket_flow_nodes。

## 3. 执行引擎 `ticket-flow.ts`（主进程新模块）

### 3.1 钩子时序

```
任意写入路径（页面 / AI / 飞书）
        │
        ▼
db.ds.insert / updateRecord（database.ts）
        │
        ▼
onRecordSave 钩子链（ticket-link → ticket-tracker → ticket-flow）
        │
        ▼
ticket-flow.onRecordSave(kind, datasetId, recordId, data, prev)
        │
        ├─ 只管工单数据集；kind=insert → 开第一个节点（状态=初始状态）+ 处理人通知（若填了）
        ├─ kind=delete → 未关闭节点标 exited（result_kind='auto'，result='工单已删除'）
        └─ kind=update：
              from = prev['状态'], to = data['状态']
              statusChanged = from !== to
              handlerChanged = prev['处理人'] !== data['处理人']
              statusChanged 和 handlerChanged 都假 → return（防重复保存）
              │
              ├─ ① 状态变了 → 关旧节点 + 开新节点（§2.3）
              ├─ ② 处理人变了（不管状态变没变）→ 通知新处理人（§4）
              └─ 全程 try/catch：失败只 logger.warn，绝不影响工单落库
```

> 注意钩子触发口径从「仅状态变更」放宽为「状态或处理人任一变更」——
> 通知挂在「处理人变了」上（§2.2），只改处理人不改状态也要能通知。

### 3.2 关键细节

- **处理人直接取工单字段**：钩子里不再覆盖「处理人」——谁填的就是谁的，
  新节点 handler_name 以落库后的字段值为准。
- **防抖**：同一工单同目标状态 60 秒内不重复开节点；同一处理人变更 60 秒内不重复通知
  （内存 Map），AI 批量改状态不刷屏。
- **回退节点不重开**：B → A（打回）时，A 状态如果之前有过节点，**新开一行**（node_index 继续
  递增）而不是复活旧行——历史不可变，审计才可信。节点表的有序行天然能重放出完整路径。
- **duration 实时显示**：当前节点 duration_minutes 为 NULL，前端按 entered_at 实时算「已停留 X」。
- **通知失败**：重试一次（webhook 网络抖动常见），仍失败记 notified=-1 + notify_error，
  不排队不补发——工单还在列表里，人看得到。

### 3.3 初始节点

新建工单时（kind=insert）开第一个节点：状态取 `data['状态'] || '待处理'`，
handler 按「处理人」字段，trigger 按来源（页面 ui / 飞书 feishu，AI 视为 ai）。
这样每个工单**从出生就有节点账**，不存在「第一段状态没有节点」的空洞。

## 4. 通知设计（v2：处理人节点 × webhook，一体触发）

### 4.1 模型

```
配置期（一次性）：
  工单设置 → 处理人节点：建「张三」，填 webhook_url = https://open.feishu.cn/.../hook/xxx
  （就这么一步。没有规则要配——通知挂在处理人上，不挂状态。）

运行期（自动）：
  工单「处理人」字段从空/旧值 → 「张三」
    → 节点表按 name 匹配：张三.webhook_url
    → sendViaWebhook(url, 文案)   ← 触发通知到张三的 webhook
```

- **谁被指派了谁就收到通知**：处理人变更即通知，与状态无关。
  「状态变到处理中」不通知——状态你自己看界面就知道，通知的价值在「这单交给你了」。
- webhook url 是普通文本，不限平台（飞书自定义机器人、钉钉、企业微信、任意接收端都行）。
- 全局兜底 webhook（现有 config.json 的飞书 webhook）保留：处理人匹配不上节点表
  或节点没配 url 时降级发全局，再没有就不发。保证「配置了就有声，没配置不炸」。

### 4.2 文案

```
📋 工单流转 · {标题}
状态：{旧状态} → {新状态}
处理人：{新处理人}
{处理结果（有才带）}
承诺：{承诺时间或「未设置」}
—— 来自 启航AI工作台
```

一期纯文本（sendViaWebhook 的 msg_type=text）。卡片（带「查看/完成」按钮）是二期。


## 6. 表结构 DDL（database.ts initSchema 追加）

```sql
-- 处理人节点（人=名字+webhook一体，流转到该节点时触发通知到其 url）
CREATE TABLE IF NOT EXISTS ticket_handlers (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  name TEXT NOT NULL UNIQUE,
  webhook_url TEXT DEFAULT '',
  enabled INTEGER DEFAULT 1,
  remark TEXT DEFAULT '',
  created_at TEXT DEFAULT (datetime('now', '+8 hours')),
  updated_at TEXT DEFAULT (datetime('now', '+8 hours'))
);

-- 流转节点实例（一次流转一行，工单的完整生命周期账本）
CREATE TABLE IF NOT EXISTS ticket_flow_nodes (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  dataset_id TEXT DEFAULT '',
  record_id INTEGER NOT NULL,
  node_index INTEGER NOT NULL DEFAULT 1,
  status TEXT DEFAULT '',
  handler_name TEXT DEFAULT '',
  handler_id INTEGER,
  entered_at TEXT DEFAULT (datetime('now', '+8 hours')),
  exited_at TEXT,
  duration_minutes INTEGER,
  result TEXT DEFAULT '',
  result_kind TEXT DEFAULT '',
  trigger TEXT DEFAULT '',
  notified INTEGER DEFAULT 0,
  notify_error TEXT DEFAULT '',
  created_at TEXT DEFAULT (datetime('now', '+8 hours'))
);
CREATE INDEX IF NOT EXISTS idx_flow_nodes_record ON ticket_flow_nodes(dataset_id, record_id, node_index);
CREATE INDEX IF NOT EXISTS idx_flow_nodes_open ON ticket_flow_nodes(dataset_id, record_id) WHERE exited_at IS NULL;
```

存量工单回填：启动迁移给每个已有工单补一条「当前状态」的初始节点
（entered_at 取记录 updated_at，node_index=1），保证账本从启用那天起完整。

## 8. 边界情况

| 场景 | 行为 |
|---|---|
| 状态 A→A 且处理人没变 | 不动节点、不通知（钩子都假 return） |
| 只改处理人、不改状态 | 不新开节点（状态没变），开放节点就地更新处理人（保证节点账能回答「这单现在在谁手里」），并通知新处理人 |
| 新建即终态 | 开第一个节点后立即关闭（result_kind='auto'），有完整的一开一关 |
| 处理人名字没建节点档案 | 不通知（节点表匹配不上），handler_name 照记、handler_id 空 |
| 处理人档案删了 | 历史节点不受影响（冗余了 handler_name）；工单设置里引用处标灰 |
| webhook 发送失败 | 重试 1 次 → notified=-1 + notify_error 留痕 |
| 删除工单 | 开放节点标关（result='工单已删除'），节点账保留（对齐 ticket_logs 不删） |
| AI/飞书建单填了处理人 | insert 时同样命中通知（钩子在数据层，来源无关） |
| 批量改状态/改处理人 | 每单独立节点；60s 防抖仅同单同目标状态/同处理人 |
