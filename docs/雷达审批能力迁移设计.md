# 智能体雷达：多智能体审批能力迁移设计

> 目标：把「多智能体监控 + 审批」能力搬进本项目的**智能体雷达**（`electron/radar/`）。
>
> **产品形态（已与需求方确认）**：
> - 用户**继续用原来的智能体对话**（Claude Code CLI / DSH App 里正常聊）；

> - qihang-ai-desktop **不接管、不代发**其他智能体的对话；它自己的对话仍然专注 **pi agent sdk**。
>
> ⚠️ **本文只覆盖「审批」这条主线。** 四项目合并与整体废弃的安排见

## 0. 结论速览

1. **监控不用搬，已经搬完了。** 本项目的 `electron/radar/` 就是 `QihangAgentHub/watcher/` 的移植版（`radar-db.ts` 头注释自述「从 qihangagenthub v2 hub-db 移植」，采集器文件一一对应）。「多智能体监控」这一半，雷达已经完整具备：8 工具只读采集、3s 轻探针、指纹增量入库、FTS5 trigram 中文检索。**本次工作是纯增量：加审批，不动监控。**

2. **「回写到别人的会话」只有两条路，而且本机已经跑通了。**
   - **Claude Code**：`~/.claude/settings.json` 的 `PermissionRequest` http hook —— 端点**挂起 HTTP 响应**等决策，返回 `hookSpecificOutput.decision`。**本机已配置**（现指向 `127.0.0.1:8790`）。
   - **DSH**：DSH 宿主插件包装 `approval.decide` 服务 —— 插件把请求 POST 给本地端点，拿决策后返回 DSH 的 `allowed-once` / `rejected`。**本机已安装**（`@local/dsh-approver` 已 link 进 `~/.dsh/profiles/desktop` 与 `acp` 两个 profile）。
   - 两者都**不需要雷达去驱动 agent**、不需要 spawn 任何进程 —— 完全符合「不接管其他智能体对话」的约束。

3. **审批不能塞进采集器。** 采集器（`HubCollector`：`listAll`/`loadMessages`/`probe`）天生只读，审批是**控制流**不是**观测流**。雷达新增一个并列的 `ApprovalService`（本地 HTTP 决策服务 + 票据 + 挂起表），采集器一个字不改。

4. **本项目已有三块现成基建可直接吃**：
   - 飞书长连接 + `card.action.trigger` + 交互卡片按钮（`electron/services/feishu.ts`）→ 飞书手机审批几乎零成本；
   - `feishuChatId` 配置项已在 `config.json.template`；
   - `node:sqlite`（无原生模块）+ 雷达库 `radar.db` → 票据表落地无打包负担。
   **只缺两处**：飞书卡片**原位更新**（`im.message.patch`）、**主动发卡到指定 chat**（现有 `replyCard` 只能回复式发送）。

5. **「永不超时」的正确落地方式**（三层，缺一不可）：
   - **票据层**：永不自动过期，一直等；
   - **传输层**：hook 客户端有 600s 硬上限 → 端点必须**先于它**返回（源项目用 540s 留 60s 余量）；超时返回空决策 → **Claude Code 回落自己的原生提示**（不静默放行）；
   - **工具层**：DSH 插件 `FETCH_TIMEOUT_MS = 3_660_000`（61 分钟），远宽裕。
   - ⚠️ **Node `http.Server.requestTimeout` 默认 300s**（Node 18+），会掐掉我们挂起 540s 的请求 → **必须显式 `server.requestTimeout = 0`**。这是本方案最容易踩的坑。

## 1. 四个项目的真实分工（含「设计了但没实现」的判定）

### 1.1 `qihang-code-approver` — **本方案的主体资产，且本机已在运行**

独立 Node daemon（端口 8790），驱动 Claude Code + DSH。它的价值不在「托管 agent」，而在**两条写回通道 + 审批状态机 + 飞书卡片**。

#### ① Claude Code 写回通道（http hook 挂起响应）

`src/index.ts:157-182`：

```ts
hookPermissionRequest: async (body) => {
  if (!body || typeof body.tool_name !== 'string') return {};       // 非法输入 → 空决策
  const decision = await Promise.race([
    center.request({ agent:'claude', sessionId:`ext-${body.session_id}`, cwd:body.cwd,
                     tool:body.tool_name, inputSummary:…, detail:… }),
    new Promise<null>(r => setTimeout(() => r(null), HOOK_WAIT_MS).unref?.()),  // 540_000ms
  ]);
  if (decision === null) return {};                                // 超时 → 空决策
  if (decision === 'deny')
    return { hookSpecificOutput:{ hookEventName:'PermissionRequest',
             decision:{ behavior:'deny', message:'已在…拒绝', interrupt:false } } };
  const out = { hookSpecificOutput:{ hookEventName:'PermissionRequest',
             decision:{ behavior:'allow', updatedInput: body.tool_input ?? {} } } };
  if (decision === 'allow_session' && Array.isArray(body.permission_suggestions) && body.permission_suggestions.length)
    out.hookSpecificOutput.decision.updatedPermissions = body.permission_suggestions;  // 会话级放行
  return out;
}
```

**契约要点**：
- **空决策 `{}` = 2xx 无决策** → Claude Code **回落自己的原生权限提示**（用户在终端里自己点）。这是极优雅的降级：**服务挂掉不等于放行**。
- **「本会话放行」不靠我们维护白名单** —— Claude Code 在 hook payload 里自带 `permission_suggestions`，我们原样回填成 `updatedPermissions`，由 Claude Code 自己去固化。**这块要原样照抄，不要自己造。**
- hook 配置（本机现状，`~/.claude/settings.json`）：
  ```json
  "PermissionRequest": [{
    "matcher": "Bash|Write|Edit",
    "hooks": [{ "type":"http", "url":"http://127.0.0.1:8790/api/hooks/permission-request",
                "timeout": 600, "onFailure":"continue" }]
  }]
  ```
  ⚠️ `timeout` 单位是**秒**；`onFailure:"continue"` = hook 失败/超时则继续（回落原生提示），**不是静默放行**。

#### ② DSH 写回通道（宿主插件包装 `approval.decide`）

`plugins/dsh-approver/lib/index.js:278-338`：

```js
const approval = ctx.get("approval");
const originalDecide = approval.decide.bind(approval);
approval.decide = async function (req, session) {
  try {
    if (daemonChild) return originalDecide(req, session);
    const res = await fetch(url, { method:'POST', signal: AbortSignal.any([ac.signal,
                        AbortSignal.timeout(FETCH_TIMEOUT_MS)]), body: JSON.stringify({
      sessionId, cwd: req.agent?.session?.header?.cwd, toolName: req.toolName,
      callId: req.callId, reason: req.reason, displayReason: req.displayReason }) });
    body = res.ok ? await res.json() : null;
  } catch { return originalDecide(req, session); }        // ← 任何异常都回落原生审批
  const decision = body?.decision;
  if (!decision || !(decision in DECISION_MAP)) return originalDecide(req, session);
  return DECISION_MAP[decision];
};
```

**契约要点**：
- 插件通过 `ctx.get("approval")` 拿到 DSH 宿主的授权服务，**包装 `decide`** —— 决策权仍在 DSH，只是「谁来回答」被换成了我们。
- **任何失败（daemon 未起/网络错误/请求中止/决策不认识）都回落 `originalDecide`** → DSH 原生终端审批照常，**不丢任何审批能力**。
- 请求体：`{sessionId, cwd, toolName, callId, reason, displayReason}`；响应体：`{decision}`。
- `inject: ["approval"]` —— 必须在 `user-approval` 之后组合；`ctx.get("approval")` 缺失时插件直接抛错。

> ⚠️ **这个插件有一个必须修掉的 bug，别照抄**：
> `DECISION_MAP`（`:27-32`）把 `allow_once` / `allow_session` / `timeout_allow` **全部**映射成 `allowed-once`；再加上 `:325-328` 只要 outcome 是 `allowed-once` 就把工具名塞进 `allowCache` —— 结果是**点「允许一次」也变成了会话级永久放行**，与按钮文案矛盾，也与 daemon 侧 DSH adapter 的语义（只有 `allow_session` 才加白名单）冲突。
> **正确做法**：`allow_session` 才写 `allowCache`；`allow_once` 只放行这一次。

#### ③ 审批状态机（本方案直接搬）

| 文件 | 内容 |
|---|---|
| `src/core/types.ts:9-25` | `ApprovalRequest`：id / agent / sessionId / cwd / tool / inputSummary(≤200) / detail(≤2000) / status(`pending\|decided\|expired`) / decision / decidedAt / decidedBy |
| `src/core/types.ts:3` | `Decision = 'allow_once' \| 'allow_session' \| 'deny' \| 'timeout_allow'` |
| `src/core/approval-center.ts:25-134` | **状态机本体**：挂起 = 一个未决 Promise；`request()` 挂起等决策；`resolve()` **先删 pending 再 resolve**（幂等的基础）；超时按策略收口；会话死亡按拒绝收口；会话级 allowlist 审计 |
| `src/core/bus.ts` | 20 行同步 pub/sub |
| `src/core/history.ts` | JSONL 追加审计 + `replay()`；重启后残留 pending 一律置 `expired` |
| `src/agents/base.ts:3-31` | `AgentAdapter` + `AgentDeps` 接缝：adapter 只负责「问要决策」，不认识 HTTP / 飞书 |
| `src/feishu/card.ts:21-66` | `buildApprovalCard` / `buildDecidedCard`：飞书 JSON 1.0 审批卡（允许一次 / 本会话放行 / 拒绝） |

**状态机关键机制**：
- **挂起即 Promise**（`:71-83`）；`resolve()`（`:87-103`）先删 pending 再 resolve → **双击幂等**，第二次点击拿 `not_pending`，卡片回 toast「已处理」。
- **降级隔离**：发卡失败只记日志（`:65-69`），飞书挂了不影响 hook/插件决策通道。
- **超时 fail-open**：`timeoutSec>0` 默认 1800s → `timeout_allow`（放行）。⚠️ 与我们「永不超时」的约定冲突，**移植时按 6.3 的方案改**。

### 1.2 `AgentHub` — 票据模型 + 3 条原生通道（借鉴，不照搬）

**3 条存活通道**（我们本方案只用其中 0 条，但它们的契约值得存档）：

| 工具 | 拦截点 | 回写 | 文件 |
|---|---|---|---|
| DSH | ACP `session/request_permission` | 写回同 id：`{outcome:{outcome:'selected',optionId}}` | `watcher/src/adapter/DshAcpAdapter.ts:631,:665` |
| OpenCode | 附加已在跑的 opencode server（`~/.local/state/opencode/service.json`，Basic auth），SSE `permission.asked` | `POST /api/session/{sid}/permission/{rid}/reply`，`{decision:'once'\|'reject'}` | `watcher/src/adapter/OpencodeAdapter.ts:383,:456,:599` |
| Codex | `codex app-server --stdio` 双向 JSON-RPC 的 `item/*/requestApproval` | `respond(rpcId,{decision:'accept'\|'decline'})` | `watcher/src/adapter/CodexAdapter.ts:90,:127` |

> 这三条都是**「本进程是协议客户端」**的形态 —— 属于 agent-direct 那种「托管式」路线，**与本方案（写回原会话）不冲突也不重合**。将来若要扩展 Codex/OpenCode，可复用。

**票据模型（语义照搬，落地成 SQLite）**：
- `approval_ticket`：`tool / session_id / call_id / approval_type / title / description / payload(JSON，含 callId) / status / decision / decision_note / decided_by / decided_at / expires_at`。
- `ApprovalService.create()`（`:47`）：同会话已有 pending 时**顶掉旧的**。
- `resolve()`（`:110`）：`status==='pending'` 守卫（先到先决）。
- `cancelByCallId()`（`:157`）：工具侧自己答复了 → 票据转 cancelled。
- `expirePending()`（`:182`）：10s 扫描过期 → `expired` + `decision=reject` + `note=timeout`。
- **关联键 = `payload.callId`**；本方案 callId 形状：Claude Code hook 用 `session_id + tool_name + 请求序号`（hook 载荷里没有原生 callId，需自造，见 6.2），DSH 插件直接用 `req.callId`。

**hook 通道被删除的原因（`docs/update/2026-11-04.md`）** —— 这决定了我们**只对 Claude Code 用 hook、且必须自己扛契约**：
1. 零真实用户；6 个 hook 宿主中 4 个从未在真实触发里验证过；
2. MiniMax 语义是坏的：hook 窗口只有 1–10s（默认 5s），而「hook 失败 = 当作没跑过」= **默认放行**，桥脚本塞不进 285s 兜底窗口；
3. 契约碎片化：同一事件名各工具 JSON 形状不同（`decision.behavior` vs `permissionDecision`），**形状错了被静默忽略 = fail-open 隐患**；
4. fail-closed 无法统一保证。
> → **我们只接 Claude Code 一个 hook 宿主**（其契约 v1 已实测验证），DSH 用插件而非 hook，规避全部四条。

### 1.3 `QihangAgentHub` — 雷达的直系上游，审批只出设计

- **`watcher/` 就是本项目雷达模块的原型**：`claude-code.ts` / `codex.ts` / `dsh.ts` / `opencode.ts` / `pi.ts` / `qoder.ts` / `trae.ts` / `trae-db-worker.ts` / `registry.ts` 一一对应；`hub-db.ts`↔`radar-db.ts`、`ingest.ts`↔`radar-ingest.ts`、`monitor.ts`↔`radar-monitor.ts`、`fingerprints.ts`↔`fingerprint-store.ts`。
- **P2 审批 = 纯设计，零实现**（已核实）：`watcher/src/**` 与 `server/src/**` 全量 grep `approval|approve|ticket|permission` **0 命中**；`hub-schema.sql` 仅 5 表，**无 `hub_approval`**；`http-server.ts` 无 `/hub/approvals*` 路由；`console.html` 5 个 tab 无审批收件箱；`src-electron/main.ts:84` 留着 `/* 通知规则 P2 再做 */`；roadmap 的勾选框**全是空的**。
- **但有两份极有价值的设计文档**：

**`docs/design/approval-channels.md` —— 逐工具通道分层**

| 层 | 工具 | 原生通道 | 验证 |
|---|---|---|---|
| **L1 ACP** | DSH | ACP `session/request_permission`（本进程是 Client） | ✅ |
| **L2 原生 API** | Codex | app-server 双向 JSON-RPC | ✅ |
| | OpenCode | server API（SSE + reply） | ✅ |
| **L3 扩展/委任** | Pi | 扩展 `tool_call` → `{block,reason}` | ✅ |
| | Claude Code | MCP `--permission-prompt-tool` | 🔷 |
| **L4 hooks 兜底**（默认不启用） | ZCode / Trae | CLI hooks | ✅/🔷 |

三条铁律：**① 本地兜底超时先于票据过期；② fail-closed；③ 观测让位**（状态机只有 running/idle，不推断 waiting_approval）。

**`docs/design/approval-flow.md` —— 票据生命周期**
```
pending → approved  →（应答放行）
        → rejected  →（应答拒绝，附言透传）
        → expired   →（兜底拒绝，note=timeout）
        → cancelled →（同会话新票据顶掉，旧挂起点唤醒拒绝）
```
- 同一 `(tool, session_id)` 同时只允许一个 pending；
- `approvalService.require({tool, sessionId, callId, approvalType, title, description, payload, timeoutSeconds})`，`UNIQUE(tool, call_id)` 幂等；
- **诚实边界（§1.1）**：原生通道下「受控会话 = 宿主托管或可附加的会话」。**本方案用 hook/插件绕开了这条边界** —— hook/插件是「配置级/插件级拦截」，能覆盖用户自己开的会话，这是它相对 ACP/JSON-RPC 的**唯一也是决定性的优势**。

### 1.4 `agent-direct` — 托管式路线的 Electron 实现（本方案不采用）

原则「软件没有自己的数据」，8 工具直连。8 个里 4 个能拦截权限：Claude Code（SDK `canUseTool`）、Codex（app-server）、DSH（ACP）、OpenCode（server API）。

**它的价值在于反面教材与两条可抄的小件**：
1. **`state-bus.ts:42-47` 的仲裁规则**：*驱动中的会话以 adapter 事件为准，探针结果整条丢弃，避免两套状态打架*。本方案不需要（我们不托管会话），但**雷达将来若加「托管会话」必须遵守**。
2. **`notification-router.ts:39` 的 `APPROVAL_HOLD_MS = 120_000`**：卡片立即出、提示音等 2 分钟，避免长命令被误判成审批。本方案在「观测态」用途上会用。
3. **`state-probe.ts`（907 行，8 个解析器）**：启发式 `waiting_approval` 探测 —— 从原生存储推断「这个会话疑似在等授权」。**本方案的第一期（只检测不决策）就用它。**
4. **它的坑（对本方案同样成立）**：
   - 审批请求**不会自己超时** —— 一个「40s 无写入 = 在等审批」的探针也会在长命令上误报；
   - 权威句柄都在 adapter 内存里，**持久化的卡片是死卡片**；
   - 两个应用驱动同一工具会打架（会话写锁 / 端口争用）。

## 3. 目标架构

```
   用户的 Claude Code CLI / DSH App（会话照旧，本进程不受影响）
        │
        │ ① Claude Code: PermissionRequest http hook ────┐
        │ ② DSH: @local/dsh-approver 插件包装 approval.decide ──┐
        │                                                    ▼
        │                          ┌──────────────────────────────────────┐
        │                          │  ApprovalService（主进程内）            │
        │                          │   • 本地 HTTP 服务 127.0.0.1:PORT       │
        │                          │     /api/hooks/permission-request (CC)  │
        │                          │     /api/hooks/dsh-approval       (DSH) │
        │                          │   • ApprovalCenter（挂起/幂等/审计）      │
        │                          │   • radar.db: radar_approval（票据落库）  │
        │                          └───────────────┬──────────────────────┘
        │                                          │ ③ 决策
        │                                          ▼
        │                          飞书卡片（允许一次/本会话放行/拒绝）
        │                          + 桌面通知 + 雷达 UI 收件箱 + 移动端中继
        │                                          │
        └──────────────────────────────────────────┘ ④ 决策回传原会话
                                                       （hook 响应 / 插件 return）
```

**与 agent-direct 路线的关系**：agent-direct 是**雷达自己开 agent 会话**（本进程是协议客户端）；本方案是**雷达只当决策中介**（agent 会话由用户自己开）。两者不冲突，**但也不能同时管同一个会话**（见 7.6）。本方案落地后，雷达依然满足「只读监控 + 不接管对话」。

**关键设计原则**：

1. **采集器与审批服务彻底分离。** `HubCollector`（`electron/radar/types.ts:42-48`）一个字不改；新增 `ApprovalService` 是独立模块。理由：v1 之所以失败，正是把 hook 注入和采集搅在一起。
2. **审批状态不进 `radar_session.state`。** 保持 running/idle 二态，审批是独立的票据流（v5「观测让位」铁律）。
3. **两类卡片必须视觉区分**：
   - **可决策卡**（hook/插件来的真请求）：带按钮。
   - **观测卡**（探针推断的疑似）：**不可点**，文案写明「该会话疑似在等待授权（由其它进程托管，本机无法代为决策）」。
   把观测卡做成可点 = 骗用户，是最伤信任的错误。
4. **挂起点与票据解耦**：HTTP 响应挂起 540s（工具侧上限），**票据本身不过期**。540s 内没人决策 → hook 返回空决策（工具回落原生提示），但票据仍留 pending；之后飞书点了照样记录决策 + 更新卡片（只是这一轮工具已经自己问过用户了）。

## 4. 逐工具写回契约（本方案的核心）

### 4.1 Claude Code — `PermissionRequest` http hook

**客户端配置**（本机现状，改 URL 即可）：

```json
"PermissionRequest": [{
  "matcher": "Bash|Write|Edit",
  "hooks": [{
    "type": "http",
    "url": "http://127.0.0.1:<PORT>/api/hooks/permission-request",
    "timeout": 600,
    "onFailure": "continue"
  }]
}]
```

**我们的响应**：
```jsonc
// 放行一次
{ "hookSpecificOutput": { "hookEventName": "PermissionRequest",
  "decision": { "behavior": "allow", "updatedInput": { /* 原样回传 tool_input */ } } } }

// 本会话放行（Claude Code 自带建议规则 → 原样回填）
{ "hookSpecificOutput": { "hookEventName": "PermissionRequest",
  "decision": { "behavior": "allow", "updatedInput": {...},
                "updatedPermissions": [ /* body.permission_suggestions 原样 */ ] } } }

// 拒绝
{ "hookSpecificOutput": { "hookEventName": "PermissionRequest",
  "decision": { "behavior": "deny", "message": "已在启航AI（飞书）拒绝", "interrupt": false } } }

// 无决策（超时/非法输入）→ Claude Code 回落原生提示
{}
```

**坑（全部来自 v1 实测 + 源项目注释）**：
- `exit 2` 在 PermissionRequest 上**无效**，必须回 JSON deny；
- **不能用 `async:true`** —— 必须同步阻塞等决策；
- `timeout` 显式给足（600s），别让客户端先放弃；
- 不用 `PreToolUse`（开销大、plan 模式下 allow 无效）；
- 沙箱内的网络请求**不触发** PermissionRequest；
- 与 SDK 宿主的 `canUseTool` **会竞态** —— 我们不跑 SDK，无此问题；
- hook 载荷里**没有原生 callId** → 需自造（见 6.2）。

### 4.2 DSH — 宿主插件包装 `approval.decide`

**插件形态**（照 `qihang-code-approver/plugins/dsh-approver`，但修掉 allowlist bug）：

```js
export function apply(ctx, config) {
  const approval = ctx.get('approval');
  if (!approval) throw new Error('approval 服务未挂载');
  const originalDecide = approval.decide.bind(approval);
  const allowCache = new Map();          // sessionId -> Set<toolName>
  approval.decide = async function (req, session) {
    const sessionId = String(req.agent?.session?.id || '');
    const toolName = String(req.toolName || 'tool');
    if (allowCache.get(sessionId)?.has(toolName)) return 'allowed-once';   // 会话级白名单命中
    try {
      const res = await fetch(daemonUrl, { method:'POST',
        signal: AbortSignal.any([req.signal, AbortSignal.timeout(3_660_000)]),
        body: JSON.stringify({ sessionId, cwd: req.agent?.session?.header?.cwd,
                               toolName, callId: req.callId, reason: req.reason,
                               displayReason: req.displayReason }) });
      const body = res.ok ? await res.json() : null;
      const decision = body?.decision;
      if (!decision) return originalDecide(req, session);       // 未知 → 回落原生
      if (decision === 'deny') return 'rejected';
      if (decision === 'allow_session') {                         // ← 只有它写白名单
        if (!allowCache.has(sessionId)) allowCache.set(sessionId, new Set());
        allowCache.get(sessionId).add(toolName);
        return 'allowed-once';
      }
      return 'allowed-once';                                     // allow_once：只这一次
    } catch {
      return originalDecide(req, session);                       // 任何异常 → 回落原生
    }
  };
}
export const inject = ['approval'];
```

**要点**：
- **回落原生是硬要求**：daemon 没起 / 网络错 / 请求中止 / 决策不认识 → 一律 `originalDecide`，DSH 原生终端审批照常。
- **`allow_once` 不能写白名单** —— 这是源插件的 bug，务必修正。
- **本机安装位置**：`~/.dsh/profiles/desktop/node_modules/@local/dsh-approver`（junction）与 `~/.dsh/profiles/acp/node_modules/@local/dsh-approver`；profile 的 `package.json` 里 `dependencies` 有 `"@local/dsh-approver": "link:..."`。
- 插件里 `watchTurns` 的回合上报（turn/start、turn/end）**本方案暂不需要**（任务完成通知是另一条线），搬过来时只留 `apply` 部分。

## 6. 三个必须先定的实现细节

### 6.1 端口与端点

- 本地 HTTP 服务端口建议 **8791**（避开 `qihang-code-approver` 的 8790，避免两个 daemon 抢端口/抢飞书长连接）。
- ⚠️ **飞书长连接唯一性**：飞书要求**专用应用** —— 同一应用的多条长连接是负载均衡关系，按钮点击会随机落到别的进程。本项目与 `qihang-code-approver` **不能共用同一套飞书 appId/appSecret**。迁移时必须给雷达配一套（或停掉旧 daemon）。

### 6.2 Claude Code hook 的 callId 合成

hook 载荷里**没有原生 callId**（v1 靠 `p.callId || p.call_id || 'hook-'+uuid` 兜底）。我们要保证幂等与「同会话只留一个 pending」，建议：

```
callId = `cc-${session_id}-${tool_name}-${hash(tool_input)}-${请求序号}`
```
- `session_id` + `tool_name` + `tool_input` 哈希 → 同一请求重放得到同一 callId → `UNIQUE(tool, call_id)` 天然幂等；
- 请求序号用进程内自增（同一毫秒内多次同参请求靠序号区分）。
- ⚠️ 但 hook 重试（Claude Code 不会自动重试 hook，实际是用户端重跑同一命令）会生成**新的** callId → 旧票据还在 pending。**决策前先检查该 `(tool, session_id)` 是否已有 pending，有则顶掉旧的**（v5 语义）。

### 6.3 「永不超时」的正确实现

| 层 | 做法 |
|---|---|
| 票据层 | `radar_approval` **不设 `expires_at`**，不写超时扫描任务；`ApprovalCenter` 不设 `timeoutSec` |
| 传输层 | hook 客户端上限 600s → 我们端点最多挂起 **540s**（留 60s 余量），超时返回 `{}` → Claude Code 回落原生提示 |
| 票据与传输解耦 | 540s 内无人决策 → hook 已返回 `{}`，但**票据仍留 pending**；之后飞书点「拒绝」→ 记录决策 + 更新卡片（工具本轮已自己问过用户） |
| DSH 层 | 插件 `FETCH_TIMEOUT_MS = 3_660_000`（61 分钟），远超 540s，无需特殊处理 |

⚠️ **Node HTTP server 默认值必须覆盖**：`server.requestTimeout = 0`（默认 300000ms 会掐断）、`server.headersTimeout = 0`（默认 60000ms，只管收头，无害但一并放开更稳）。

### 6.4 「本会话放行」语义在各工具的差异

| 工具 | 「本会话放行」怎么实现 | 注意 |
|---|---|---|
| Claude Code | 回填 `updatedPermissions = body.permission_suggestions` | **不要自己维护白名单** —— Claude Code 自己固化规则 |
| DSH | 插件侧 `allowCache`（sessionId → Set<toolName>） | ⚠️ 只有 `allow_session` 才写；`allow_once` 不写 |

## 7. 风险与坑位清单

### 7.1 「永不超时」≠ 工具会永远等

工具侧有各自的等待上限（Claude Code hook 600s、DSH 宿主自身也可能超时）。我们能做的是：**票据不过期 + 决策总能被记录 + 超时不静默放行**。要在飞书卡片和雷达 UI 上如实说明，避免用户以为「不点就永远挂着」。

### 7.2 持久化的票据是「死卡片」

挂起 HTTP 响应 / 插件 await 的句柄在**服务端进程内存**里，进程一死就没了。所以：
- 落库只为了**审计与历史查询**；
- UI 判定「可点」的依据必须是**进程内 pending 表**（`ApprovalCenter.pending`），不是数据库的 `status='pending'`；
- 重启后残留 pending 一律标记 `expired`（照 `qihang-code-approver/src/core/history.ts:47-53`）。

### 7.3 探针误报

「tool_use 无 result」与「`npm install` 跑了 3 分钟」在存储层**长得一样**。观测卡必须：标注「疑似」、120s 稳定窗后才提示、永不可点。

### 7.4 飞书四坑

1. `im.message.patch` 的 `message_id` 是 **path 参数**；
2. 卡片按钮回调**必须 3s 内响应**，只能回 toast，慢活丢后台；
3. **同一应用的多条长连接是负载均衡关系** → 必须专用 appId；
4. 飞书卡片 JSON 1.0：form 容器必须在根节点、输入框 `max_length` 上限 1000（超了整卡 400）。

### 7.5 安装引导要「非破坏性」

写 `~/.claude/settings.json` 时：**先读 → 只改 `hooks.PermissionRequest` → 保留其余键与格式 → 写回**。绝不覆盖整个文件。用户可能同时用 `qihang-code-approver` 的 hook —— 要检测到并提示「已有 hook，是否替换/共存」。

### 7.6 与旧 daemon / agent-direct 共存

- 本机当前 `~/.claude/settings.json` 的 hook 指向 `127.0.0.1:8790`（`qihang-code-approver`）。**两个 daemon 同时在跑 → hook 请求随机落到其中一个**（取决于谁先起）。迁移必须二选一：停掉旧 daemon，或改指向新端口。
- DSH 插件同理：`@local/dsh-approver` 目前 link 到 `D:/projects/qihang-code-approver/plugins/dsh-approver`。迁移需要改 link 指向新插件目录（或让插件的 daemonUrl 可配置，两个 daemon 都能服务）。
- `agent-direct` 若也在跑，它会 **spawn 自己的 DSH/Codex 会话** → 与用户自己开的会话抢会话写锁。**本方案不 spawn 任何东西，天然无冲突**；但要提醒用户别同时用两个工作台管同一工具。
