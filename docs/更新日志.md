> - 历史条目（2026-07-08 ~ 2026-09-27，共 166 次提交）由 git 提交记录回填，按日期分组，保留 commit 短哈希便于追溯：`git show <hash>`。

- 条目前缀类型：`feat` 新增 / `fix` 修复 / `refactor` 重构 / `perf` 优化 / `chore` 杂项与依赖 / `docs` 文档 / `build` 打包发布

- 日期以提交日期为准；同一批改动合并为一个条目，不按 commit 逐条罗列

### 🛡️ 审批与通知通道

- `chore` Claude Code 通知通道回归 `Stop` 单通道（撤销 StopFailure 与「工作台接管」）：实测确认 Claude Code 把「正常完成」和「异常终止」分成两个 hook——`Stop` 只在正常收尾时触发且**会等 hook 返回**（`decision:block + reason` 能把追问注回原终端会话执行），`StopFailure` 是「只通知」事件、CLI 报错后 1~2 秒即退回提示符**完全不等 hook**，因此无法用于续聊。按用户要求删掉 `StopFailure` 全链路（`task-notify` 归一化、`server` 端点、`approver` 处理、`claude-hook-deploy` 部署项，并从 `~/.claude/settings.json` 移除该 hook，仅保留 `PermissionRequest` + `Stop`），同时撤销所有「工作台后台接管」路径：`radar:followup` 与飞书卡片对 claude 外部会话在快速通道窗口外一律提示「请回到原 Claude Code 窗口继续」，不再 SDK resume 新建会话（此前会把一次点击变成会话链增殖，实测 16 秒内新建 10 个会话）。净化残留的 `cwdOfSession/lastCwdBySession`。

- `fix` StopFailure 不能用来「继续对话」——实测（v2.1.312）`claude -p` 因模型错误终止后**立即退回提示符**（进程 1~2 秒内退出），完全不等该 hook 返回：窗口设 120s、塞入追问仅 1.4s 后 CLI 已结束，未产生续跑。即 `StopFailure` 是「只通知」事件，`decision:block` 对它无效。据此已整体撤销 StopFailure 与所有后台接管路径（详见上方 `chore` 条目），Claude Code 通知/继续回归 `Stop` 单通道。

- `fix` 审批长轮询被客户端 300 秒超时掐断：Node 内置 fetch（undici）默认 headersTimeout/bodyTimeout 都是 300s，人在飞书上隔几分钟才点「允许」，挂起等决策的响应必被掐断（DSH/pi-gate 插件表现为「审批服务不可用」）。现先发响应头、挂起期间每 30 秒写一个空格保活（JSON 允许前导空白，`res.json()` 不受影响），`/api/hooks/permission-request`、`/api/hooks/dsh-approval`、`/api/hooks/claude-stop` 全部生效。

- `fix` OpenCode 审批镜像补带项目目录：`qihang-gate` 插件在 `permission.asked` 镜像请求里补 `cwd`（取事件 location，兜底 `ctx.location.directory`），飞书审批卡能显示是哪个项目；此前该字段为空，卡片上目录显示为 `?`。

- `fix` OpenCode 审批噪声与漏弹修掉：此前插件在 `ctx.permission.hook("evaluate")` 里对**每一次**工具权限求值都送审，opencode 本来就放行的只读命令（`git status`、`git diff`）也会弹飞书审批卡（实测一天攒了 45 张，且全部标注「来源：工作台强制送审」），还把「放行」升级成「询问」，导致终端对只读操作弹 `Permission required`；反过来，opencode 规则真正命中 `ask` 的动作反而没有独立可靠的送审通道。现改为**双通道**：opencode 终端照常弹自己的原生权限提示（永不冻结、永不改变 opencode 判定），插件旁路只监听 `permission.asked` 事件把**真正的权限请求**镜像成飞书审批卡，飞书决策经 `ctx.permission.reply()` 回灌**同一扇窗口**，终端先答的飞书镜像卡自动作废（新增 `POST /api/hooks/opencode-approval-cancel`）。镜像前先探测请求是否仍然存活，避免非交互模式被 opencode 自动拒绝时刷出无效卡片。opencode 审批卡按钮按其语义改为「允许一次 / 允许并记住（项目级）/ 拒绝」——opencode 的 `always` 会持久保存项目级放行规则，与 claude/dsh 的「本会话放行」不是一回事，文案不再误导。

- `feat` OpenCode 接入雷达与飞书：外部 opencode 会话（CLI/桌面端）现在与 Claude Code 同款——回合完成/失败自动推飞书任务卡与雷达通知，工具审批可改由飞书审批卡逐次放行，卡上「▶️ 继续 / 接着问」的追问回到**用户开着的那扇 opencode 窗口**原会话继续执行（不接管不 fork）。实现方式是 opencode v2 官方全局插件 `qihang-gate`（随审批通道启动自动部署到 `~/.config/opencode/plugins/qihang-gate.ts`，文件变更 opencode 自动热重载）：插件用 `ctx.event.subscribe` 收 `session.execution.succeeded/failed` 上报回合、收 `permission.asked` 镜像审批、用 `ctx.session.prompt()` 把追问注入原会话；工作台侧新增 `/api/hooks/opencode-approval`（登记飞书审批卡）、`/api/hooks/opencode-decision`（插件轮询取决策）、`/api/hooks/opencode-approval-cancel`（终端先答则撤卡）、`/api/hooks/opencode-followup`、`/api/hooks/opencode-policy` 五个端点，雷达会话详情页与通知栈的「插入对话」放行 opencode。审批取决策用「建卡 + 25 秒一轮短轮询」而不是一条长连接：HTTP 客户端有 5 分钟响应体超时，人在飞书上隔几分钟才点「允许」时长连接会先被掐断，决策就送不回终端。

- `feat` OpenCode 额外加严配置：新增配置项 `opencodeEscalateActions`（逗号分隔动作名，如 `shell,edit`），把 opencode 规则本为放行的动作额外升级为待审批，从而也走飞书审批，**默认留空**——只有 opencode 自己命中 `ask` 的动作才送审，填多了会把日常读操作也变成审批，日常不建议开；想要「高危操作走飞书审批」应改用 opencode 自己的 `permissions` 规则（只命中危险命令），设置页已给出推荐片段。可在「设置 → 智能体审批与雷达通知 → OpenCode 接入插件」里配置。

## v0.15.0（2026-11-14）

> 本版主线：可用性细节大修——修复 AI 对话采集与全文搜索的两类底层缺陷，完成今天页与雷达页整合，跟进/日志板块去噪。

### 智能体雷达：数据采集修复

- `fix` Trae 助手消息全部丢失：Trae 库的 `history_v2.message_id` 存的是「触发这一轮的用户消息 ID」，助手 task 消息自身 ID 在快照表查不到，原采集器拿助手消息 ID 关联落空（0 行），AI 内容整体被丢。现助手消息改用骨架里的 `reply_to_message_id` 关联快照（用户消息仍用自己的 ID），实测每轮 4-10 段叙述 + 1-21 个工具调用完整入库。
