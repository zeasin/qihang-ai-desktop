# 设计方案：飞书对话并入对话页（2026-10-31）

## 一、现状与问题

当前飞书消息的处理链路（`electron/main.ts` `feishuMessageHandler`）：

1. 消息进来 → `feishu-router` 解析目标项目（路由/选择卡片/重跑按钮均与本方案无关，保持不动）
2. `recordFeishuTask()`（task-runner.ts）在 `plan_tasks` 落一行任务记录
   （`source='feishu'`、`trigger_type='now'`、`task_type='note'`）+ `task_executions` 一行
3. 以任务 id 建会话 `task_<taskId>`（`prj_sessions.source='feishu'`），消息落 `prj_messages`
4. `runPi` 执行 → 结果卡片回飞书

由此产生两个错位：

- **对话页看不到飞书会话**：ChatView 只拉 `getSessionsBySource('ui')`，飞书会话（source='feishu'）完全不可见；
- **任务页混入一次性问答**：飞书问一句答一句也变成一条"任务"，而任务页语义应该是**自动运行的后台任务**（一次性定时 / 循环调度）。

「继续 X」追问链路依赖"最近一条飞书任务行"定位会话（`plan_tasks WHERE source='feishu' ORDER BY id DESC`）。

## 二、目标形态（已确认的两个决策）

| 决策点 | 结论 |
| --- | --- |
| 软件内打开飞书会话能否继续追问 | **可以**。同一会话双向共享上下文（飞书「继续」与软件内追问落同一会话），软件内回复不回推飞书 |
| 存量飞书一次性任务 | **一次性迁移为纯会话**：删 `plan_tasks` / `task_executions` 行，保留会话与消息 |

改造后：

- **对话页** = 统一收件箱：UI 发起 + 飞书发起的会话合并展示，飞书会话带「飞书」徽标；
- **任务页** = 只剩后台任务（`trigger_type` 为 once/cycle，含 notify_feishu 推送类）。

## 三、数据层

### 3.1 飞书首条消息不再落任务表

新流程直接建会话，不经过 `plan_tasks`：

- session id：`feishu_<Date.now()>_<rand>`（与 UI 的 `session_...` 风格一致，不再耦合任务 id）；
- `db.chat.createSession(sessionId, projectId, 正文前30字, 'kb', 'pi', 'feishu')`；
- user / assistant 消息照旧落 `prj_messages`。

### 3.2 prj_sessions 增加来源锚点（可选但建议）

加列 `origin_chat_id TEXT DEFAULT ''`（沿用 `ALTER TABLE ... try/catch` 惯例），存飞书 `chat_id`。用途：

- 「继续」按飞书会话（群/私聊）隔离：每个群各自续各自的最近对话，而不是全局最近一条；
- 为将来"软件内回复回推飞书"留映射钩子。

### 3.3 存量迁移（启动时一次）

```sql
DELETE FROM task_executions WHERE task_id IN (
  SELECT id FROM plan_tasks WHERE source='feishu' AND trigger_type='now');
DELETE FROM plan_tasks WHERE source='feishu' AND trigger_type='now';
```

- 会话 `task_<id>`（source='feishu'）及其消息**保留**，自动出现在对话页（带徽标）；
- 迁移瞬间若有 in_progress 的飞书任务：后续 `db.task.update` 变成 UPDATE 0 行的 no-op，会话消息照常落库，无害；
- 注意**不能**走 `db.task.remove()`——它会连会话一起删，必须用上面的 SQL 只删任务行。

## 四、主进程改造（main.ts / task-runner.ts）

### 4.1 feishuMessageHandler 瘦身

- 删除 `recordFeishuTask` 调用与 `feishuTaskId` / `feishuExecId` 簿记、`updateTaskFailed`、`notifyTaskChanged`；
- 改为建会话 + `addMessage`，然后照旧 `runPi`；
- **复用现有 chat:* 事件族**：`onDelta`/`onDone`/`onError` 里除落库、回卡片外，同步 `emit('chat:delta'|'chat:done'|'chat:error', { sessionId, ... })`。ChatView 的 `streams` 本来就按 sessionId 消费这组事件——飞书会话在软件内**实时流式可见、列表自动显示 ⏳**，零 UI 改动即可获得；
- 可选一行：`relayClient.syncSession(sessionId)`，让移动端也同步这条会话；
- 「已接单，执行中…」「卡片换项目重跑」「⏱ 已中止（部分输出）」等飞书侧交互全部保留。

### 4.2 追问核心抽公共函数（task-runner.ts)

抽出 `runFollowupTurn({ sessionId, project, question, model, onDone, onError })`：加 user 消息 → 组装 kb 提示词 → `runPi` → 回复落库。两个入口共用：

- `followUpTask(taskId, ...)`：**保留**，继续服务后台任务的追问（TaskDetailView / PlannerView），只是内部改调公共函数，任务簿记不变；
- 新增 `followUpFeishuSession(sessionId, question, ...)`：无任务簿记，按会话的 project_id 定位项目目录，事件走 `chat:*` + `task:followup:*`（后者只用于飞书端回包，不带 taskId 语义时可只走 chat:*）。

### 4.3 「继续 X」定位改造（main.ts）

旧：`plan_tasks WHERE source='feishu' AND task_type != 'coding' ORDER BY id DESC LIMIT 1`。

新：`db.chat.latestBySource('feishu', originChatId)`：

```sql
SELECT * FROM prj_sessions
WHERE source='feishu' AND (IFNULL(origin_chat_id,'')='' OR origin_chat_id=?)
ORDER BY updated_at DESC LIMIT 1
```

- 防重入改用主进程内存 `Set<sessionId>`（飞书轮次执行中再发「继续」→ 回「执行中，请稍候」，等价于旧逻辑的 `status==='in_progress'` 检查）；
- 无会话时文案改为「还没有可继续的飞书对话，请先发一条消息」。

### 4.4 database.ts 新增

- `chat.latestBySource(source, originChatId?)`（配合 3.2 的列；列未加时忽略第二参）；
- `createSession` 增加可选 originChatId 透传。

## 五、对话页（ChatView.vue）

1. **列表合并**：`loadSessions()` 改为同时拉 `getSessionsBySource('ui')` 与 `getSessionsBySource('feishu')` 合并（无需改 preload，API 已存在），过滤条件放宽为
   `s.source === 'feishu' || s.mode === 'general' || !s.project_id`；
2. **来源徽标**：会话条目标题旁 `session.source==='feishu'` 时渲染 `<span class="conv-badge">飞书</span>`；聊天区 header 同样显示，并加 title 提示「来自飞书，在软件内回复不会推送到飞书」；
3. **运行状态/流式**：自动生效（见 4.1），无额外代码；
4. **软件内续聊**：`selectSession` 已把项目选择器同步为会话所属项目，`chatContext()` 已能从会话 project_id 解析目录，`API.chat.send` → `runChatTurn` 对已存在会话幂等（source 保持 'feishu'）——基本开箱即用。注意一点：飞书轮次用的是带项目路径引导的 kb 提示词，而 `runChatTurn` 是 general agent；如需完全对齐，可在 `runChatTurn` 里按会话 mode==='kb' 追加同一段引导语（建议做，一行模板复用）；
5. **删除会话**：现有 `deleteSession` 即可，无任务行牵连。

## 六、任务页收敛（PlannerView / TaskDetailView）

- `visibleNoteTasks` 防御性过滤：`.filter(t => !(t.source === 'feishu' && t.trigger_type === 'now'))`（正常情况下迁移后不会再出现，防外部写入兜底）;
- 顺手清理死分支：PlannerView 的 `:disabled="selectedTask.source === 'feishu' ..."`、TaskDetailView 的 `isFeishuTask`；
- UI 手动「立即执行」型任务（`trigger_type='now'`）语义**保持现状**，不在本次范围。

## 七、边界与风险

| 场景 | 处理 |
| --- | --- |
| 迁移时有飞书任务在跑 | 任务行更新 no-op，会话消息照常落库 |
| 卡片「换个项目重跑」 | 语义变为"新建一条会话在新项目重跑"，逻辑保留 |
| 项目被删除后打开旧飞书会话 | 落入"未分组"；发送时项目不存在回落默认项目（followup 核心已有同款回落） |
| 会话正在执行时软件内发消息 | `runChatTurn` 与飞书轮次对同一 session 并发写消息——与现状 UI 双开窗口风险同级，接受；后续可在主进程加 per-session 锁 |
| 「继续」无历史会话 | 文案改为"还没有可继续的飞书对话" |
| 429 限流挂起 | 沿用 2026-10-31 决策：不设超时，软件内可在列表看到 ⏳ 长亮，飞书端等回应 |
